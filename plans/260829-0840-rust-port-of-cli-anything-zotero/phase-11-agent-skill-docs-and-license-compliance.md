# Phase 11: Agent Skill, Docs and License Compliance

## Overview

Make the Rust CLI usable by the audience it was built for — AI agents — and discharge the Apache-2.0
obligations that attach to a derivative work.

## Requirements

**Functional**
- `SKILL.md` regenerated against the Rust CLI and validated by a real agent session
- Installation, migration and architecture documentation
- Apache-2.0 compliance: license text, §4b statement of changes, third-party license bundle
- `docs/SECURITY.md` documenting the eval-endpoint exposure

**Non-functional**
- Documentation must state plainly what is *not* ported and what changed

## Architecture

### Agent-facing skill

Upstream ships `cli_anything/zotero/skills/SKILL.md` (285 lines) generated by `skill_generator.py`
from `templates/SKILL.md.template`. Agents consume it to learn the command surface.

The Rust port needs an equivalent generator that introspects the **actual** `clap` tree, so the skill
can never drift from the binary:

```
zotero-cli --dump-command-tree --json   # hidden, machine-readable command inventory
        │
        ▼
  tools/gen-skill.rs  →  SKILL.md
```

A hidden `--dump-command-tree` flag is additive (not in the Python surface, so no compatibility
concern) and makes the skill generator trivially correct. It also gives the Phase 3 inventory test
its data source.

The skill must state explicitly:
- the excluded/changed behaviours, so agents do not attempt them as normal v1 commands
- that `--json` works at any level
- that in `--json` mode errors arrive on **stdout**
- the exit-code contract
- that `js` is arbitrary privileged Zotero JavaScript execution and must only be used after explicit
  user intent
- that AI analysis and embedding commands can send item context to configured endpoints, with the
  HTTPS/loopback policy from Phase 7

### Documentation set

| Document | Content |
|---|---|
| `README.md` | What it is, install, quick start, agent example |
| `docs/INSTALL.md` | Per-platform install; macOS Gatekeeper guidance (from Phase 2) |
| `docs/MIGRATION.md` | Python → Rust: what changed, what was dropped, how to run both |
| `docs/ARCHITECTURE.md` | The four backend surfaces; the `immutable=1` trade-off (D4) |
| `docs/SECURITY.md` | The XPI eval endpoint; loopback binding; threat model |
| `docs/COMPATIBILITY.md` | Generated from `PARITY-REPORT.md` |

`docs/MIGRATION.md` must be blunt about the five deltas:

1. `repl` removed; bare invocation prints help instead of entering a shell
2. macOS AppleScript bridge fallback removed — install the XPI plugin
3. `--experimental` direct-SQLite write path removed; the three command names now use the JS bridge
4. Seven DOCX commands not yet ported (Phase 12) — keep Python for those, or use the static path
5. `app check-update` no longer polls upstream; use the package manager

### Apache-2.0 compliance

Upstream is Apache-2.0 with **no `NOTICE` file**, so there is no NOTICE-propagation obligation. The
obligations that do apply to a modified derivative:

| Obligation | Action |
|---|---|
| §4a — include the license | Ship `LICENSE` (Apache-2.0) in the repo and every release archive |
| §4b — **state changes** | `NOTICE-CHANGES.md`: this is a modified derivative of `PiaoyangGuohai1/cli-anything-zotero` @ `e42a930e`, ported from Python to Rust, with the five deltas enumerated |
| §4c — retain notices | Preserve copyright/patent/trademark notices in any file carried over — notably `bootstrap.js` and `manifest.json` |
| Attribution | Credit upstream in `README.md` with a link |
| Third-party | Generate `THIRD-PARTY-LICENSES.md` for all Rust crates (`cargo-about`) |

Trademark: Apache-2.0 §6 grants no trademark rights. Avoid implying endorsement by upstream or by
Zotero. Resolve naming alongside plan Open Questions 1 and 2.

## Implementation Steps

1. Add the hidden `--dump-command-tree --json` flag emitting the full inventory: paths, args, flags,
   defaults, help text.
2. Write the skill generator consuming that inventory.
3. Generate `SKILL.md`; add a CI check that fails if the committed skill is stale relative to the
   binary. The generator must filter deferred/dropped commands out of ordinary examples and render
   them only as warnings/deprecation notes.
4. Write the documentation set, with `MIGRATION.md` leading on the five deltas.
5. Generate `THIRD-PARTY-LICENSES.md` and wire it into releases (already scaffolded in Phase 2).
6. Write `NOTICE-CHANGES.md` per §4b.
7. Verify `bootstrap.js` and `manifest.json` retain upstream notices; add attribution headers to any
   Rust file that is a close translation of an identifiable upstream module.
8. **Validate with a real agent session**: give an agent only `SKILL.md` and the binary, and have it
   complete a realistic task (find items, inspect one, add a note) with no other context.
9. Generate `docs/COMPATIBILITY.md` from `PARITY-REPORT.md`.

## Success Criteria

- [ ] `SKILL.md` generated from the live command tree; CI fails if stale
- [ ] An agent completes a realistic multi-step task using only `SKILL.md` and the binary
- [ ] `SKILL.md` documents the JSON-errors-on-stdout contract, `--json` at any level, and the exit-code table
- [ ] `SKILL.md` warns that `js` is privileged arbitrary Zotero execution and excludes it from normal examples
- [ ] `SKILL.md` and `docs/SECURITY.md` document AI endpoint payload/credential exposure and the HTTPS/loopback policy
- [ ] Deferred/dropped commands are not presented as normal usable commands in generated agent docs
- [ ] All five migration deltas documented in `docs/MIGRATION.md`
- [ ] `LICENSE` present in repo and in every release archive
- [ ] `NOTICE-CHANGES.md` satisfies Apache-2.0 §4b, naming the upstream repo and commit
- [ ] `THIRD-PARTY-LICENSES.md` generated and shipped
- [ ] Upstream notices retained in all carried-over files
- [ ] `docs/SECURITY.md` documents the eval endpoint and its threat model
- [ ] `docs/ARCHITECTURE.md` documents the four surfaces and the D4 trade-off
- [ ] No naming or wording implies endorsement by upstream or by Zotero

## Risk Assessment

| Risk | Mitigation |
|---|---|
| Generated skill drifts from the binary | CI staleness check makes drift a build failure |
| Agent cannot use the CLI from the skill alone | Step 8 is a real validation run, not a review |
| Agent follows generated docs into deferred stubs or privileged raw JS | Generator filters by compatibility class; privileged commands get warning-only documentation |
| License compliance treated as boilerplate and done wrong | Obligations enumerated concretely above with a per-item checklist |
| Naming implies upstream endorsement | Explicit success criterion; resolve Open Questions 1 and 2 before release |
| Migration doc understates what is missing | Deltas listed explicitly and reviewed against `PARITY-REPORT.md` |
