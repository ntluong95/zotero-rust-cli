# Command Compatibility Matrix — Python → Rust

Source: `PiaoyangGuohai1/cli-anything-zotero` @ `e42a930e` (v1.2.1)
Generated by static analysis of `cli_anything/zotero/zotero_cli.py` · **96 leaf commands**

**Compatibility classes**

- **Exact** — identical JSON keys/types/values and exit code after normalizing non-deterministic fields (absolute paths, timestamps, PIDs, generated keys).
- **Semantic** — identical JSON *schema* and exit-code semantics; values may legitimately differ (network, Zotero translators, float ties).
- **Changed** — intentional, documented behavioural break.
- **Deferred** — excluded from v1; gated post-v1 phase.
- **Dropped** — not ported.

Global flag accepted at **every** level (via `_JsonAwareGroup`): `--json`. Root-only: `--backend {auto,sqlite,api}`, `--data-dir`, `--profile-dir`, `--executable`, `--version`.

**Full finding list** (`plan.md`'s Zotero 10 impact table, recovered verbatim): (1) WAL mode enabled,
CRITICAL, retro-fixes landed P4 code; (2) XPI `strict_max_version: 9.0.*` unloadable on 10, CRITICAL;
(3) Local API write support, OPPORTUNITY, drives the Phase 6 redesign; (4) Local API key/consent +
`Zotero-Server-ID`, HIGH; (5) HTTP hardening (Host allowlist, UA/Origin rejection), HIGH; (6) plural
`ZoteroPane.getSelected*()`, MEDIUM, affects `collection use-selected`/`session use-selected`
semantics; (7) attachment stored-path/`setType` tightening, HIGH, Phase 7; (8) FTS5 rewrite +
saved-search auto-migration, MEDIUM, covered above; (9) no change to port/auth/schema fundamentals.

**Backward compatibility is explicit, not implied:** Zotero 7/8/9 keep the JS Bridge write path
unchanged; the port detects capability at runtime rather than assuming a Zotero version. This is a
compatibility *gate* (Phase 14), not a cutover — no currently-Exact or currently-Semantic
classification in this matrix is downgraded by the Zotero 10 adaptation itself; only the two rows
above gain documented, evidence-based nuance.

**31 of 96 total CLI commands implemented**: 20 catalog/read commands (Exact) + 3 Phase 8 vector
store commands (Semantic) + 8 Phase 5 `session *` commands (Exact). 23 of 24 Phase 4 commands are
Exact (only `session use-selected` remains), all 3 Phase 8 commands are complete, and 8 of 9 Phase 5
`session *` commands are Exact (`session use-selected` also remains, same connector-client blocker).

**Reconciling concurrent work.** The Phase 8 semantic slice (`0529cb8`) and the session-state slice
(this document's own account below) were built in parallel on separate machines/sessions and landed
on `main` within an hour of each other, diverging from a shared parent. Reconciled via
`git rebase origin/main`, which auto-merged `cli.rs`/`lib.rs` cleanly but left one genuine
compile-breaking gap: `item build-index`'s dispatch arm was written against the *pre-lazy-runtime*
`dispatch_command` (i.e. against a `runtime` variable that existed unconditionally at the top of the
function) and never picked up the `let runtime = build_runtime();` pattern the session slice
introduced to every other runtime-needing arm, because that refactor didn't exist yet when the
semantic arm was written. Fixed as part of the rebase, verified against Python source
(`item_build_index_command`, `zotero_cli.py:1211-1215`, is the only one of the three semantic
handlers that calls `current_runtime(ctx)` — confirms `semantic-search`/`similar` correctly have no
runtime construction at all, and `build-index` correctly needs one).

**8 of 9 Phase 5 `session *` commands now Exact.** Only `session use-selected` remains (same
connector-client blocker). This slice found a real architectural bug, not just new commands: every
command handler built `RuntimeContext` — including its 2-call HTTP probe — unconditionally, which was
invisible through 23 previously-landed commands (all of which legitimately needed it) until the first
runtime-free commands (`session status` etc.) landed and immediately produced an `http_calls`
`Mismatch` against Python's `[]`. Fixed by making runtime construction a lazy closure called only by
the handlers that need it. See `phase-05-http-surfaces-connector-local-api-and-runtime.md` for the
full account, including manual cross-process persistence verification the harness's one-command-per-
fixture design can't prove on its own.

Runtime foundation landed alongside these five (not independently
command-tested, but exercised by all of them): `paths` (Zotero
install/profile/data discovery), `session` (read-only), `http` (connector +
Local API client), `db` (read-only SQLite layer, `mode=ro&immutable=1`),
`runtime` (`RuntimeContext` + status payload), `output` (`--json`/human
rendering, including the human-mode list format that is deliberately **not**
valid JSON, matching Python), `error` (domain-error → exit 1 contract), `cli`
(clap surface, `--json` accepted at any level via `global = true`).

### Verification beyond the golden fixtures

A code-review pass (line-by-line diff of every new Rust module against its Python
source) and a dynamic-testing pass (constructing 23 new scenarios not covered by
the existing golden fixtures — SQL-fallback search paths, ambiguous-reference
errors, numeric-ref edge cases, empty/group-library fixture states, real HTML
note content) both ran against this vertical slice before it was considered
done. Real bugs found and fixed:

- **Whitespace-padded numeric refs misclassified as key lookups** (`item get " 5 "`,
  `item find --collection " 1 "`) — Python's `int(str(value))` trims whitespace;
  Rust's `is_numeric_ref` didn't. Fixed in `db.rs` (now `.trim()`s before parsing,
  at every call site that follows the check).
- **Windows `file:` URI used native backslash separators** — SQLite's URI spec
  requires `\` → `/` on Windows (Python does this via `Path.as_posix()`); an
  untranslated backslash path would have broken every read command on that
  platform. Fixed in `db::connect_readonly`. Undiscovered by the harness (dev/CI
  is Darwin-only so far) — confirmed by code review, not dynamic testing.
- **Negative `--limit` on `item find`'s Local-API-hit path** used `.max(0)`-clamped
  truncation instead of Python's `list[:limit]` negative-slice semantics (drops
  the last `|limit|` items rather than clamping to empty). Fixed with a
  `python_slice_to_limit` helper in `catalog.rs`.
- **`session::session_library_id`** (currently dead code — the 5 shipped commands
  use the separate, already-correct `session_library_ref` path) silently
  substituted a default on a non-numeric session value instead of erroring,
  which would have silently operated on the wrong library once a future write
  command wires it in. Fixed to return `Result` and error loudly, before it
  becomes load-bearing.
- Minor: regexes in `note_html_to_text` were recompiled on every call, and
  `note_preview` recomputed the HTML-to-text conversion `note_html_to_text`
  already did. Hoisted to `LazyLock` statics; `note_preview` now takes the
  already-converted text.
- Minor: `local_api_get_json` silently defaulted to an empty body on a read
  failure instead of propagating the error; fixed to propagate I/O errors
  while still matching Python's `errors="replace"` lossy-UTF-8 decoding for
  malformed (not merely absent) response bytes.

**Known, accepted divergences** (deliberate, documented — not defects to fix):

- A missing `zotero.sqlite` file returns a clean `DomainError` (exit 1,
  structured message) in Rust instead of Python's uncaught `FileNotFoundError`
  (raw traceback, also exit 1 by CPython default, but with no `{"error": ...}`
  structure in `--json` mode). Same for an item/collection numeric ref that
  overflows `i64` (Python: uncaught `OverflowError` traceback; Rust: clean
  "not found" `DomainError`). Both are deliberate improvements over accidental
  Python behavior — see `error.rs`'s module doc comment.
- `note_html_to_text` doesn't decode legacy semicolonless HTML entities (e.g.
  `&nbsp` without the trailing `;`) the way Python's `html.unescape` does —
  the `html-escape` crate doesn't implement that WHATWG legacy table. Zotero's
  own note editor always emits well-formed, semicolon-terminated entities, so
  this only affects notes with hand-crafted/scraped legacy HTML. Not fixed;
  see `db.rs`'s `note_html_to_text` doc comment.
- **Resolved (2026-08-29), user decision:** when Zotero/the connector/Local API
  is completely unreachable (not merely disabled — nothing listening on the
  port at all), `app status`'s `connector_message`/`local_api_message` fields
  contain OS/runtime-specific transport error text (Rust's `ureq::Error`
  `Display` vs. Python's `urllib`-derived `<urlopen error [Errno 61] ...>`
  text) that cannot be made byte-identical across languages, and reproducing
  one transport library's exception prose in the other is not a real
  compatibility contract worth chasing. **Decision: accept the divergence,
  scoped narrowly.** A dedicated `zotero-unreachable` harness fixture
  (`harness/commands.tsv` row 97, no fake HTTP server started at all — a real
  closed TCP port) normalizes **only** `connector_message` and
  `local_api_message` to `<CONNECTION_REFUSED>`, and **only** for that fixture
  state (`harness/normalize.py`). Everything else — JSON structure, both
  reachability booleans, `http_calls: []`, exit code — is compared unweakened.
  `app status`'s other fixtures (`local-api-off`'s real HTTP 403, etc.) are
  untouched and stay Exact with no normalization at all. Implemented and
  verified **Exact**: see the Migration Progress table below.

## Contracts that must be preserved verbatim

| Contract | Detail |
|---|---|
| `--json` position | Accepted at root, group **and** command level (`item find X --json`). |
| JSON error channel | In `--json` mode errors print to **stdout** as `{"error": "..."}` — not stderr (`zotero_cli.py:2665`). |
| Human error channel | Without `--json`, `ClickException.show()` → **stderr**; `RuntimeError` → `Error: {msg}` on stderr. |
| Exit codes | `results.exit_code_for`: `ok=false` → 1; `status` ∈ {partial_success, error, failed, timeout} → 1; else 0. |
| Result envelope | `{action, ok, status, code?, error?, ...}` from `results.result_payload`. |
| JSON encoding | `ensure_ascii=False, indent=2`; falls back to `ensure_ascii=True` when stdout cannot encode. |
| Env vars | See the 17-variable status table below |
| Default paths | session `~/.config/cli-anything-zotero/session.json` (**all** platforms, incl. Windows); vectors `~/Zotero/cli-anything-vectors.sqlite`; data dir fallback `~/Zotero`; port fallback `23119` |
| Binary names | `zotero-cli` (primary), `cli-anything-zotero` (alias) |

## Approved intentional breaks

| # | Behaviour | Python | Rust | Rationale |
|---|---|---|---|---|
| 1 | Bare invocation (`zotero-cli`, no subcommand) | Enters REPL, **blocks on stdin** | Prints help, exits 0 | A blocking stdin read is the worst failure mode for a non-interactive agent. |
| 2 | `item move-to-collection` | `--experimental` mandatory; direct SQLite write; Zotero must be **closed** | Bridge composition (`add_to_collection` + `remove_from_collection`); Zotero **running**; no flag | Verified: no bridge path exists upstream. Reimplementation is new work and strictly more usable. |
